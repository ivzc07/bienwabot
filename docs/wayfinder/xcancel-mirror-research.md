# xcancel and the X Mirrors - Research

Wayfinder ticket [#57 "Find out whether xcancel and the Nitter mirrors are a free X source"](https://github.com/ivzc07/bienwabot/issues/57), part of map [#50](https://github.com/ivzc07/bienwabot/issues/50): settle whether a free public mirror of X can feed Rebe's news leg, before the operator pays X anything.

Research date: 2026-07-27.
This is a companion to the [X home-timeline access research](x-timeline-access-research.md), which priced the official route at ~$15-30/month and rejected scripting X with the operator's own login.
Read that one first; the field inventory here is deliberately laid against its field inventory.

Every claim below was tested by fetching the URL, not by reading a blog post about it.
Where a page was only read rather than exercised, it says so.
Where something could not be settled either way it says "unverified" rather than guessing.

---

## The short version

xcancel is alive but is **not** the route.
It now sits behind a browser-verification challenge that a Python HTTP client cannot pass, and its RSS is gated behind a manual email whitelist.

There is a free route, and it is better than expected - but it is a different service.
**FxEmbed** (`fxtwitter.com` / `api.fxtwitter.com`) serves per-account RSS feeds and a documented JSON API with **every engagement count the paid X API returns**, no key, no login, 1000 requests/minute.
`nitter.net` per-account RSS is a working second source with a narrower field set.

That changes the recommendation in [#51](https://github.com/ivzc07/bienwabot/issues/51) from "pay X" to "try free first".

## 0. What actually happened this morning

The trigger for this ticket was Rebe posting `https://xcancel.com/HedgieMarkets/status/2081534588485296565` at 08:55, ranked out of Hacker News.
It is worth being precise about that, because it is easy to read it as evidence that the bot can already fetch a mirror.
It is not.

Grepping `rebe_agent/` for `xcancel`, `nitter`, `twitter.com` and `x.com` returns **no matches**.
Nothing in the bot knows what a mirror is.
The xcancel URL arrived as the `url` field of a Hacker News story, through the existing keyless Algolia call in `feeds.py`, and the pipeline passed it along like any other link.

The HN record itself is now inconsistent with that.
Querying Algolia for that tweet ID returns exactly one story - objectID `49068738`, "AI companies are shredding rare books", 676 points, created `2026-07-27T12:32:12Z` - and its `url` today is `https://twitter.com/HedgieMarkets/status/2081534588485296565`, not the xcancel form.
The most likely explanation is that the URL was edited on HN between the bot's read and this research, which HN moderators routinely do; that specific cause is **unverified**.
What is verified is that xcancel links are common on HN: an Algolia URL-restricted search for `xcancel.com` reports **274 stories**.

So the finding underneath the trigger is small but real - mirror URLs already flow into the bot as ordinary HN links, and nobody chose that.
It says nothing about whether the bot can read a mirror on purpose, which is what the rest of this document tests.

## 1. What xcancel is, and what is left of the Nitter network

### xcancel is a Nitter instance

Its own [about page](https://xcancel.com/about) opens with "XCancel is an instance of Nitter", links [zedeus/nitter](https://github.com/zedeus/nitter), and reports **Version 2026.07.26-26144b6** - built yesterday.
Nitter is an alternative front-end that fetches from X server-side and renders plain HTML: "No JavaScript or ads", "All requests go through the backend, client never talks to Twitter", "Uses Twitter's unofficial API (no developer account required)" ([about](https://xcancel.com/about)).

### How the survivors survive

The [Nitter README](https://github.com/zedeus/nitter) answers the guest-token question in a boxed note:

> "Running a Nitter instance now requires real accounts, since Twitter removed the previous methods."

The [Creating session tokens](https://github.com/zedeus/nitter/wiki/Creating-session-tokens) wiki page spells out what that means.
An instance operator maintains a `sessions.jsonl` file of real X account cookies - `auth_token` and `ct0` per account - generated by running `create_session_browser.py <username> <password> [totp_secret]`, which drives a browser through X's login for each account.
The page opens with a warning: "Running a large public instance is difficult, and is not feasible with a small amount of accounts."
On the risk to those accounts it is candid: "It's a good idea to use proxies/VPNs if creating many sessions, but it's unknown how much this affects your risk of getting banned."

The maintainer's own [announcement](https://github.com/zedeus/nitter/discussions/1212) (February 2025, still pinned) says the same thing from the operator's side: "Hosting an instance now is difficult and expensive, but not impossible. For a small/private instance you can do it for free quite easily, but a large public instance is a different story."

**So the mechanism is a pool of real, disposable X accounts, held by the instance operator, at that operator's risk.**
This matters for the risk section below, and it matters for reliability: the supply of live instances tracks how many people are willing to keep burning accounts.

### Who is still up

The [instances wiki](https://github.com/zedeus/nitter/wiki/Instances), last edited 2026-07-11, lists one official instance (`nitter.net`) and nine public ones, all marked online and working: xcancel.com, nitter.poast.org, nitter.privacyredirect.com, lightbrd.com, nitter.space, nitter.tiekoetter.com, nuku.trabun.org, nitter.catsarch.com, nitter.kareem.one.
Its Tor and I2P tables are empty.

The community uptime tracker [status.d420.de](https://status.d420.de/) gives the health picture, last updated 2026.07.16 16:35 UTC - eleven days stale at the time of writing, which is itself a signal about how closely this network is watched.
It scores xcancel at **97% all-time** availability with RSS marked available and current health "❓", nitter.net at 95% with RSS available, and marks nitter.privacyredirect.com as **not healthy**.
Only three of the ten - nitter.net, xcancel, nitter.poast.org - are marked as having RSS enabled at all.
Its [about page](https://status.d420.de/about) documents a 900-second check interval, a JSON feed at `/api/v1/instances`, and one sentence the operator should read:

> "Please do not use instances listed here for scraping! Instead host your own nitter instance, so public instances can be used by less tech savy people and not get overrun by you."

That is the community asking us not to do the thing this ticket is investigating.
It is not law, and it is not a licence term, but it is the stated wish of the people paying for the servers.

## 2. What a mirror can actually serve

### The home timeline: confirmed impossible

The ticket's hypothesis is right and can be stated flatly.
A Nitter instance authenticates to X as **its own** pool of throwaway accounts, never as the operator's account, so the "home timeline" it could theoretically produce would be the follow graph of an anonymous burner, not hers.
Nitter's own [roadmap](https://github.com/zedeus/nitter) lists "Account system with timeline support" as an unbuilt future item, and the [about page](https://xcancel.com/about) says the same in the future tense: "In the future a simple account system will be added that lets you follow Twitter users."
There is no route, on any instance, to the operator's own home timeline without her login.

**The whole-following-graph idea dies here.**
Everything below is about hand-picked accounts instead.

### What xcancel serves today: one narrow window, and it is closing

Tested with `curl`, a browser user-agent, the bot's own `rebe-agent/0.1` user-agent, and a real headless browser.

| Route | Result |
|---|---|
| `xcancel.com/HedgieMarkets/status/2081534588485296565` | **200, 91,915 bytes of real tweet HTML** |
| `xcancel.com/OpenAI` | 200, 6,822 bytes - "Verifying your browser…" |
| `xcancel.com/karpathy` | 200, 6,822 bytes - "Verifying your browser…" |
| `xcancel.com/search?f=tweets&q=OpenAI` | 200, 6,822 bytes - "Verifying your browser…" |
| `xcancel.com/AnthropicAI/with_replies` | 200, 6,822 bytes - "Verifying your browser…" |
| `xcancel.com/i/lists/1234` | 200, 6,822 bytes - "Verifying your browser…" |
| `xcancel.com/karpathy/status/2079610838143623371` | 200, 6,822 bytes - "Verifying your browser…" |

That 6,822-byte page is a proof-of-work challenge.
Its source self-hosts a WASM blob (`window.CAP_CUSTOM_WASM_URL = "/antibot/assets/cap_wasm_bg.wasm"`) and carries `<noscript><meta http-equiv="refresh" content="0; url=/antibot/captcha" /></noscript>`, so a client with no JavaScript is sent to an image captcha.
A real headless browser fetched it too and got the same "Checking your browser" text, which means passing it is not a matter of setting a better user-agent.

The one page that came back with real content is the exact URL from this morning's HN story, and it came back on **every** attempt regardless of user-agent, while a fresh status URL on the same instance was challenged on every attempt.
The natural reading is that a page already warm in xcancel's cache is served without the challenge and a cold path is not; that specific mechanism is **unverified**.
What is settled for our purposes is the operational conclusion: **xcancel cannot be used as a fetch target for arbitrary post URLs from a script.**

`xcancel.com/robots.txt` is `User-agent: *` / `Disallow: /`.

### xcancel RSS: exists, gated behind a human

This was the highest-value thing to test, because a working `/<handle>/rss` would have been a one-line addition to `FEEDS` in `feeds.py`.

`https://xcancel.com/OpenAI/rss` returns **302** to `https://rss.xcancel.com/OpenAI/rss`, which returns **200 `application/rss+xml`** - about 1.4 KB of well-formed RSS whose single item is:

> "RSS reader not yet whitelist! Plain request with just the ID will be ignored! Please send an email rss [AT] xcancel [DOT] com with the reason why you want your RSS feed reader to be whitelist and this ID: …"

Same result for `sama`, `AnthropicAI` and `karpathy`.
The ID is not stable: three different user-agents against the same URL produced three different IDs, so the whitelist keys on something that includes the client's user-agent, and a whitelisted string would have to be pinned to whatever exact headers the bot sends.

A human-in-the-loop email approval, keyed to a fingerprint we would have to freeze, is not a source `rebe-agent` should depend on.
**xcancel RSS: rejected.**

### Every other Nitter instance: closed to scripts

Same request - `GET /OpenAI/rss` with the bot's own user-agent - against all nine other instances.

| Instance | Result |
|---|---|
| **nitter.net** | **200, 30,048 bytes, `application/rss+xml`, 20 real items** |
| nitter.poast.org | 403 - "Verifying your browser \| Nitter" |
| nitter.privacyredirect.com | 200 HTML - "Making sure you're not a bot!" |
| lightbrd.com | 403 - Cloudflare "Attention Required!" |
| nitter.space | 403 - Cloudflare "Attention Required!" |
| nitter.tiekoetter.com | 403 - instance error page |
| nuku.trabun.org | 522 - origin unreachable |
| nitter.catsarch.com | 403 |
| nitter.kareem.one | 403 - Cloudflare "Just a moment…" |

Repeating the exercise against each instance's *status* page (`/karpathy/status/2079610838143623371`, browser user-agent) produced the same wall: 503, 403, 403, bot-check page, 403, 403, 522, bot-check page.
Not one of the nine served a parseable tweet.

**Of ten public Nitter instances, exactly one is machine-readable, and it is the official one.**

### nitter.net: RSS works, HTML does not

`nitter.net` per-account RSS works with a plain `httpx`-style GET and the bot's own user-agent, no cookies, no key.

| Handle | Result |
|---|---|
| `nitter.net/OpenAI/rss` | 200, 30,048 bytes, **20 items** |
| `nitter.net/sama/rss` | 200, 27,850 bytes, **20 items** |
| `nitter.net/karpathy/rss` | 200, 55,535 bytes, **21 items** |
| `nitter.net/GoogleDeepMind/rss` | 200, 22,792 bytes, **18 items** |
| `nitter.net/AnthropicAI/rss` | **404** - `User "AnthropicAI" not found`, three times running |
| `nitter.net/anthropicai/rss` | 200, 18,729 bytes - `Anthropic / @AnthropicAI` |

That last pair is a real trap and worth writing down: **the same account 404s in one letter-case and resolves in another.**
It looks like a poisoned negative cache entry rather than genuine case-sensitivity, since `OpenAI` and `GoogleDeepMind` both work in mixed case; the cause is **unverified**.
Any build on this route needs to treat a 404 as "retry lowercase", not as "account gone".

The HTML side of nitter.net is effectively dead to us.
`nitter.net/OpenAI`, `nitter.net/OpenAI/status/2081794871795589485` and `nitter.net/search?f=tweets&q=OpenAI` each returned **HTTP 200 with a zero-length body** - to `curl`, to a headless browser, and to a third independent fetcher.
So nitter.net gives RSS and nothing else, which matters because RSS is where the engagement counts are missing.

`nitter.net/robots.txt` returns 200 with an empty body.

## 3. The route that actually works: FxEmbed

Chasing the counts problem led somewhere better than any Nitter instance.

**FxEmbed** is the service behind `fxtwitter.com`, `fixupx.com` and `fxbsky.app` - the "put `fx` in front of the link" tool people use to fix X embeds in Discord and Telegram.
It is [open source under MIT](https://github.com/FxEmbed/FxEmbed), 4.8k stars, actively developed (the response header on today's fetch read `x-powered-by: fixtweet-main-75d6ddd-2026-07-27T18:16:00`, built hours before this test), documented at [docs.fxembed.com](https://docs.fxembed.com/), and running on Cloudflare.

It is not a side effect of the embed service - the public API is an advertised feature.
`fxtwitter.com/robots.txt` says so in a comment block addressed to humans:

> "Do you want an easy way to fetch posts but Elon Musk wants to charge you $100 per month? Did you know we have a fetch API you can use for free, no API keys required? Check out the docs at https://docs.fxembed.com to learn how to use it"

### Per-account RSS - the `feeds.py` fit

The [RSS & Atom feeds guide](https://docs.fxembed.com/guide/advanced/rss-atom-feeds/) documents `https://fxtwitter.com/{handle}/feed.xml` (RSS 2.0), `feed.atom.xml` (Atom), and `media.xml` for media-only posts, with optional `count` (1-100, default 90), `with_replies`, `safe` to hide sensitive posts, and `lang`.

Fetched today with the bot's own user-agent, no key:

| Feed | Result |
|---|---|
| `fxtwitter.com/OpenAI/feed.xml?count=20` | 200, 20,916 bytes, 19 items |
| `fxtwitter.com/sama/feed.xml?count=20` | 200, 17,002 bytes, 20 items |
| `fxtwitter.com/AnthropicAI/feed.xml?count=20` | 200, 18,863 bytes, 20 items |
| `fxtwitter.com/karpathy/feed.xml?count=20` | 200, 27,041 bytes, 14 items |
| `fxtwitter.com/GoogleDeepMind/feed.xml?count=20` | 200, 19,972 bytes, 18 items |

All `application/rss+xml`, all well-formed RSS 2.0 with `title`, `link`, `guid isPermaLink="true"`, `pubDate` in RFC 822, `enclosure` for the first image, and an HTML `description` in CDATA carrying the full text and any quoted post as a `<blockquote>`.
`link` and `guid` are canonical **x.com** URLs, not mirror URLs, which is exactly what we want to store and post.

This parses with the code already in `feeds.py`.
The existing `feed_items` walk reads `title`, `link`, `guid`, `pubDate` and `description` from `channel/item`, and `_moment` already handles RFC 822.
A new source is genuinely a one-line entry in `FEEDS`, per handle, with no new machinery - which is what the ticket hoped for and did not get from Nitter.

### The JSON API - where the counts live

RSS carries no engagement numbers, so if [#54](https://github.com/ivzc07/bienwabot/issues/54) wants them as a ranking signal, use the JSON API instead.
The [API overview](https://docs.fxembed.com/api/introduction/) documents base URL `https://api.fxtwitter.com`, all current endpoints under `/2/`, machine-readable OpenAPI at `https://api.fxtwitter.com/2/openapi.json`, cursor pagination, and a rate limit of **1000 requests per minute per IP address** - "generous enough for most legitimate applications", with self-hosting offered if it is not.

The endpoint list covers `/2/status/{id}`, `/2/status/{id}/reposts`, `/2/status/{id}/quotes`, `/2/thread/{id}`, `/2/conversation/{id}`, `/2/profile/{handle}`, `/2/profile/{handle}/statuses`, `/2/profile/{handle}/media`, `/2/search`, `/2/trends` and `/2/typeahead`.

`GET /2/profile/OpenAI/statuses` returned 200 with 71,793 bytes and 20 fully-hydrated posts **with counts included**.
That single call replaces both the discovery pass and the enrichment pass, which is a better shape than RSS for the worthiness gate, at the cost of a small JSON adapter instead of a `FEEDS` line.

Twelve consecutive calls to `api.fxtwitter.com` all returned 200.
Twelve consecutive calls to `nitter.net/OpenAI/rss` all returned 200 in 0.55-0.73s.
No throttling was observed at that volume on either; nothing near the documented 1000/min ceiling was tested.

### What is lost versus the paid API

**Through FxEmbed JSON: almost nothing that matters.**
All five `public_metrics` counts plus views are present, which is the fact that decides this ticket - the worthiness gate in [#54](https://github.com/ivzc07/bienwabot/issues/54) can be built on free data.
The genuine losses are `context_annotations` (X's semantic topic hints, a nice-to-have relevance signal we would have to replace with keyword matching), `protected` (not observed on the author object, though a protected account's posts should simply not be served - **unverified**), and `alt_text` on media (not observed).

**Through any RSS route: the counts.**
Neither FxEmbed RSS nor nitter.net RSS carries a single engagement number.
This is the trade at the heart of the decision - RSS is the zero-machinery option and the JSON API is the option with the ranking signal, and they are the same service, so it is a choice and not a constraint.

**Through nitter.net RSS specifically:** no counts, no `possibly_sensitive`, no quote metadata beyond the rendered blockquote, and its `link`/`guid` point at `nitter.net` rather than `x.com`, so URLs need rewriting before anything is stored or posted.
Its one advantage over FxEmbed RSS is that `guid` is the **bare 19-digit post ID**, which is the posted-store key the dedup fog in [#50](https://github.com/ivzc07/bienwabot/issues/50) is looking for, handed over with no parsing.
FxEmbed RSS carries the same ID as the last path segment of the `x.com` permalink, which is one `rsplit` away.

## 5. Reliability

**Rate limits.** FxEmbed documents 1000 requests/minute per IP ([API overview](https://docs.fxembed.com/api/introduction/)). Twelve consecutive calls returned 200. Nothing near the ceiling was tested. Nitter publishes no limit; twelve consecutive nitter.net RSS calls returned 200 in 0.55-0.73s. The nitter.net feed declares `<ttl>40</ttl>`, so polling faster than every 40 minutes buys nothing.

**Uptime history.** [status.d420.de](https://status.d420.de/) puts xcancel at 97% all-time and nitter.net at 95%, on a 900-second check interval. No comparable public tracker for FxEmbed was found; that is a real gap in this research and its uptime is **unverified**.

**How often instances die.** The honest answer is: constantly, and the evidence is in the numbers above. Ten instances are listed as online and working in the wiki, and **nine of them refused a scripted request today**. The wiki was last edited 2026-07-11 and the status tracker last ran 2026-07-16, so the published picture is already stale by days-to-weeks. A list exists to fail over across - the wiki table, the `/api/v1/instances` JSON, and the [Twiiit](https://twiiit.com) random-instance redirector - but as of today a failover chain across public Nitter instances would exhaust itself and land on nitter.net every time.

**What breaks the day this goes dark.** Structurally, nothing catastrophic, because `WebCandidates.fetch` in `feeds.py` already gathers with `return_exceptions=True` and logs each failure as "did not answer, skipping it this run". A dead X source degrades to HN plus the eight existing RSS feeds, which is exactly today's behaviour. The failure worth designing against is not the loud one but the quiet one: a mirror that returns **200 with a bot-check page**, which is what six of the nine instances did today. That parses as zero items, not as an error, so the run logs nothing and the group silently loses its X leg. Any build on this route needs a content assertion - "this response contained at least one item, and the item had a post ID" - not just `raise_for_status()`.

**The mitigation the community itself recommends** is self-hosting. Nitter self-hosting means running a pool of real X accounts and accepting their ban risk, which is the thing [#51](https://github.com/ivzc07/bienwabot/issues/51) rejected. FxEmbed self-hosting is a Cloudflare Worker deploy ([guide](https://docs.fxembed.com/deployment/)), but its [credentials page](https://docs.fxembed.com/deployment/credentials/) was not read and whether a self-hosted instance needs X account cookies is **unverified**. A cheaper mitigation that needs no hosting: read from **two** sources - FxEmbed as primary, nitter.net RSS as fallback - since they are independently operated and independently authenticated.

## 6. Legality and risk

Three separate questions get conflated here, so take them one at a time.

**Does any risk land on the operator personally? No.**
This is the decisive difference from the rejected browser-session route in [#51](https://github.com/ivzc07/bienwabot/issues/51).
That route automated the operator's own Premium account, and [X's automation rules](https://help.x.com/en/rules-and-policies/x-automation) name permanent suspension of that account as the penalty.
On the mirror route, **no X account of the operator's is involved at any point** - no login, no cookie, no OAuth token, no credential handed to anyone.
The bot makes an HTTPS request to `fxtwitter.com` or `nitter.net` and never touches an X server.
X has nothing to suspend, because there is nothing of hers in the transaction.
That is a categorical difference, not a difference of degree, and it is the single strongest argument for this route.

**Is the bot doing anything wrong? Very little, and it is contractual rather than legal.**
Reading a public RSS feed the publisher documents and advertises is ordinary use, not scraping.
FxEmbed's `robots.txt` does not merely permit it - it invites it in prose and links the docs.
Note that the same file sets `Disallow: /*/status` and `Disallow: /profile` for generic crawlers while explicitly allowing `ChatGPT-User`, so the *documented feed and API endpoints* are the sanctioned path and crawling the HTML pages is not; use `feed.xml` and `api.fxtwitter.com`, never the site's own HTML.
`xcancel.com/robots.txt` is a blanket `Disallow: /`, which - together with its browser challenge - is an unambiguous "do not automate me". Honouring that costs us nothing since the route is unusable anyway.
The nitter-status maintainers ask directly that their listed instances not be used for scraping ([about](https://status.d420.de/about)); a handful of RSS polls per day against a documented, `ttl`-declaring feed is a defensible reading of that, and hammering it would not be.

**Where does the real exposure sit? On the mirror operators, and it is worth being honest that we would be free-riding on it.**
They are the ones running real X accounts against X's unofficial API in plain breach of [X's Terms](https://x.com/en/tos), which prohibit accessing the service "by any means (automated or otherwise) other than through our currently available, published interfaces".
The Nitter wiki keeps [DMCA response templates](https://github.com/zedeus/nitter/wiki/DMCA-templates) for instance operators, arguing mere-conduit safe harbour under 17 U.S.C. § 512(a) in the US and Directive 2001/29/EC in the EU, on the grounds that "all content is proxied from Twitter and is not stored on our servers".
Those arguments have not, as far as this research found, been tested in court - **unverified**.
The practical consequence is not legal liability for us but supply risk: this route exists at the pleasure of volunteers absorbing a risk on our behalf, which is a reason to poll gently, to cache, and to keep the HN/RSS fallback healthy rather than letting it rot.

**One editorial risk this route does not remove.** Whatever the source, resharing someone's post with their handle and avatar into a WhatsApp group is the act the "whose posts are off-limits" fog in [#50](https://github.com/ivzc07/bienwabot/issues/50) is about. FxEmbed gives `possibly_sensitive` and a `safe=1` feed parameter as free hard filters. It does not give `protected`, and it does not make the editorial call.

## 7. The screenshot angle

[#55](https://github.com/ivzc07/bienwabot/issues/55) needs a tweet card and the paid API returns none.
Three candidates, tested.

**A mirror page rendered to an image - workable but fiddly, and not on xcancel.**
The xcancel status page is genuinely tweet-shaped: `.main-tweet` contains the avatar, display name, a blue verified badge titled "Verified blue account", the `@handle`, the full text, the media gallery, an absolute timestamp ("Jul 27, 2026 · 12:18 AM UTC"), and a stats row.
It is a clean, self-contained element that a headless browser could clip to with a single selector.
Two problems.
The page also renders 34 tweets of replies, so a naive full-page screenshot is enormous and the clip is mandatory rather than optional.
And more decisively, **we cannot fetch that page** - the browser challenge in section 2 blocks every cold status URL, and nitter.net serves an empty body.
Rendering a mirror page is possible in principle and not available in practice.

**`publish.x.com/oembed` - free, allowed, and not a card.**
Fetched today: 200, no auth, returning `author_name` ("Hedgie"), `author_url`, and an embed `html` blockquote.
But the text is X's own truncation ending in "…" with a `pic.twitter.com` link, and the payload contains no avatar, no media URL, no counts and no timestamp beyond the linked date.
It renders into a card only by loading X's `widgets.js` in a browser, which means shipping X-hosted script into our render step for a strictly worse field set than we already have.
It is a comparison point, not a candidate.

**Render our own card from FxEmbed JSON - the recommendation.**
The inventory in section 4 has everything a card needs: avatar URL, display name, handle, full text, media URLs with `width` and `height`, absolute timestamp, and all five counts.
That is more than the xcancel page shows (which omits quotes and bookmarks) and far more than oembed gives.
Our own HTML/CSS template cannot break under us, can be tuned for the JPEG-quality-80 re-encode that [#52](https://github.com/ivzc07/bienwabot/issues/52) found Evolution applies to every image, and can be rendered in Spanish-friendly type.
This is the same conclusion [#51](https://github.com/ivzc07/bienwabot/issues/51) reached, now with the fields available for free.

## Recommendation

**Yes - there is a free route good enough to make paying X unnecessary, and it is FxEmbed, not xcancel.**

**Primary: FxEmbed.**
Either `https://fxtwitter.com/{handle}/feed.xml?count=20&safe=1` as plain RSS 2.0, which drops straight into `FEEDS` in `feeds.py` with no new machinery at all, or `GET https://api.fxtwitter.com/2/profile/{handle}/statuses`, which is one JSON call per handle and returns likes, reposts, replies, quotes, bookmarks and views alongside the text.
**Take the JSON route.** The counts are the whole reason [#54](https://github.com/ivzc07/bienwabot/issues/54) wanted the X API, they are free here, and a small JSON adapter is a cheap price for the ranking signal.
Documented rate limit 1000 req/min per IP, no key, no login, MIT-licensed and self-hostable if it disappears ([docs](https://docs.fxembed.com/api/introduction/)).

**Fallback: `https://nitter.net/{handle}/rss`.**
Independently operated and independently authenticated, so it fails separately.
No counts, mirror-domain URLs that need rewriting to `x.com`, and the lowercase-retry quirk from section 2.
Its `guid` is the bare 19-digit post ID, which is the posted-store key.

**Rejected: xcancel and the other eight public Nitter instances.**
xcancel challenges every cold page with a WASM proof-of-work, gates RSS behind a manual email whitelist keyed to a user-agent fingerprint, and sets `Disallow: /`.
The other eight refused a scripted request today.

**Rejected as a source, retained as a comparison: `publish.x.com/oembed`** - truncated text, no counts, no media, and it needs X's widget script to become a card.

### What the source list becomes

**The whole following graph is impossible.** No mirror can serve a private home timeline, and no mirror ever will without the operator's login - section 2 settles that.

So the source becomes **a hand-picked set of AI accounts, one `feeds.py`-shaped entry per handle**, in exactly the spirit of the eight vendor RSS feeds already there.
Verified reachable today through FxEmbed: `@OpenAI`, `@sama`, `@AnthropicAI`, `@karpathy`, `@GoogleDeepMind`.

**The operator has to name that list.**
It is an editorial decision, not a technical one, and it is the one open item this ticket hands back.
The starting question for her: which ten to twenty accounts does she actually read on X for AI news?
Practical notes for whoever assembles it - each handle costs one request per poll, `authority` per handle can carry the same weight the vendor feeds do, and org accounts (`@OpenAI`) behave like the existing announcement feeds while individuals (`@sama`, `@karpathy`) are the commentary layer HN gives us today.

### What this changes about [#51](https://github.com/ivzc07/bienwabot/issues/51)

That research recommended paying ~$15-30/month for `GET /2/users/{id}/timelines/reverse_chronological`.
Nothing in it was wrong.
But it was answering "how do I read *her home timeline*", and this ticket shows that question has an expensive answer and a cheap adjacent one.

The paid route buys exactly two things the free route does not: **her actual follow graph** as the curation signal, and **a contractual relationship** with the data's owner instead of a dependency on volunteers.
The free route gives up the follow graph in exchange for a hand-picked list, keeps every engagement count, costs nothing, requires no OAuth dance, and puts **zero risk on the operator's account**.

**Build the free route first.**
It is a smaller change to `feeds.py` than the paid route is to anything, the operator can see real X posts in the group this week, and if the hand-picked list turns out to be a worse curator than her own timeline, the paid route is still there and this document has already priced it.

### Flags / verify-at-build

- **FxEmbed uptime is unverified.** No public status page was found. Treat it as unproven and keep the nitter.net fallback wired from day one.
- **A bot-check page parses as zero items, not as an error.** Six instances returned 200 with a challenge body today. Assert on content - at least one item, with a post ID - not on HTTP status.
- **The nitter.net lowercase quirk.** `AnthropicAI` 404s, `anthropicai` works. Retry lowercase before concluding an account is gone.
- **`protected` and `alt_text` were not observed** on FxEmbed's author and media objects. Check before building the off-limits gate on them.
- **`context_annotations` has no free equivalent.** If topic hints matter to the worthiness gate, budget for keyword matching instead.
- **FxEmbed self-hosting may still need X account cookies.** [The credentials page](https://docs.fxembed.com/deployment/credentials/) was not read. Read it before treating self-hosting as a risk-free escape hatch.
- **The community asks not to be scraped.** [status.d420.de](https://status.d420.de/about) says so directly. Respect the `ttl`, cache, and do not poll faster than the cadence needs.
